# تشغيل أحمدكو في بيئة الإنتاج

هذا الدليل يميّز بين ملفات المشروع وبين الإعدادات التي لا يمكن إثباتها إلا داخل حساب Supabase وGoogle Play Console.

## 1. قاعدة البيانات — نفّذ بعد مراجعة النسخة الاحتياطية

في Supabase → SQL Editor، راجع ثم نفّذ الملفات التالية بصلاحية مالك المشروع:

1. `supabase/driver_order_lifecycle.sql` — إنشاء الطلبات المحمية، دورة عمل السائق، وتسجيل مستحقاته.
2. `supabase/customer_order_tracking.sql` — عرض طلبات صاحب رقم الهاتف بعد التحقق من الهاتف عبر OTP.
3. `supabase/production_hardening.sql` — منع الإدخال والقراءة المباشرين لجدول الطلبات من العملاء المجهولين، وإجبار إنشاء الطلبات عبر الدالة المقيّدة.

نفّذ ملف `production_hardening.sql` بعد ملفات دورة الطلب والتتبع. لا تنفّذ الملفات نفسها من أكثر من نافذة في الوقت نفسه. لا تحذف الجداول الموجودة ولا تنشئ بدائل لها.

**مهم:** إضافة ملفات SQL إلى GitHub لا تشغّلها في قاعدة البيانات. لا تعتبر أي وظيفة مفعّلة حتى تنفّذها وتختبرها في مشروع Supabase الصحيح.

## 2. إعداد مصادقة العملاء

صفحة تتبع الطلبات تستخدم Supabase Phone OTP. في Supabase → Authentication:
- فعّل Phone Auth.
- اربط مزود SMS صالحاً، واختبر وصول الرسائل إلى أرقام فلسطينية فعلية.
- اضبط حدود إرسال الرموز وفترة صلاحيتها وحماية إساءة الاستخدام.
- لا تسمح بعرض الطلبات إلا عبر RPC `get_my_customer_orders` بعد تحقق رقم الهاتف.

إذا لم يصل SMS أو لم يكن مزود الرسائل مضبوطاً، لا تعرض الصفحة الطلبات ولا تدّع نجاح التحقق.

## 3. تحقق أمان قاعدة البيانات قبل استقبال طلبات حقيقية

من Supabase → Database → Tables / Policies، راجع كل جدول وتأكد من الآتي:
- `orders`: القراءة والتعديل للمدير المصرّح به فقط، وقراءة السائق لطلباته المسندة فقط. الإدخال العام يكون عبر RPC المقيّدة لا عبر إدخال مفتوح للجدول.
- `drivers`: السائق يرى ملفه فقط؛ لا يستطيع اعتماد نفسه أو تغيير `is_active` أو `application_status`.
- `driver_earnings`: لا يستطيع السائق أو العميل تعديل مبالغ العمولة أو حالة الدفع.
- `delivery_rates` و`business_settings`: الكتابة للمدير فقط.
- `stores` و`product_categories` و`products`: القراءة العامة للمتاجر/المنتجات النشطة فقط، والكتابة للمدير فقط.
- `user_roles`: لا يستطيع المستخدم منح نفسه دور admin أو تغيير أدوار الآخرين.
- تأكد أن دالة `is_admin()` آمنة، وتستخدم `auth.uid()`، ولا تعتمد على قيمة يرسلها المتصفح.

لا تضع `service_role` أو مفاتيح سرية في صفحات HTML أو ملفات GitHub. مفتاح Supabase publishable/anon مخصص للواجهة العامة، وأمان البيانات يعتمد على RLS والسياسات ودوال RPC.

## 4. اختبارات قبول إلزامية

نفّذ هذه الاختبارات على بيانات تجريبية وبمستخدمين منفصلين قبل الإطلاق:
1. زبون ينشئ طلباً بمنطقة ووسيلة نقل لها سعر نشط؛ يظهر الطلب مرة واحدة فقط في لوحة الإدارة.
2. طلب بمسار أو مركبة بلا سعر نشط يُرفض دون إنشاء طلب.
3. زبون آخر لا يستطيع قراءة طلبات الأول حتى لو عرف رقم الطلب.
4. سائق غير معتمد لا يرى طلبات ولا يحدّث حالة.
5. سائق معتمد لا يرى ولا يحدّث إلا الطلب المسند إلى حسابه.
6. انتقال السائق يكون: assigned → picked_up → delivered؛ إعادة المحاولة لا تكرر سجل المستحقات.
7. مع عمولة 15%، إذا كانت أجرة التوصيل 20 شيكلاً، تكون عمولة المكتب 3 شواكل ومستحق السائق 17 شيكلاً.
8. رقم هاتف غير موثّق لا يعرض أي طلب؛ رقم موثّق يعرض الطلبات المطابقة فقط.
9. حساب غير إداري لا يستطيع فتح بيانات لوحة الإدارة أو تنفيذ عملياتها من API.
10. جرّب تسجيل الخروج، انتهاء الجلسة، ضعف الشبكة، وتحديث التطبيق على جهاز Android فعلي.

## 5. توقيع Android والنشر

- أنشئ مفتاح توقيع Release واحداً، احتفظ بنسخة احتياطية مشفّرة منه، ولا تغيّره بين التحديثات.
- أضف الأسرار الأربعة المطلوبة إلى GitHub Actions Secrets كما في `ANDROID_RELEASE_SETUP.md`.
- شغّل Workflow الإصدار يدوياً؛ لا تشارك المفتاح أو كلمات المرور في المحادثات أو المستودع.
- تحقق من توقيع APK وAAB وبصمة شهادة الإصدار، ثم اختبر التثبيت والتحديث على جهاز فعلي.
- ارفع AAB إلى Google Play Console، وأكمل بيانات المتجر وسياسة الخصوصية وتصنيف المحتوى وإفصاحات البيانات واختبارات Play المطلوبة.

نجاح Workflow أو وجود ملف APK لا يعني وحده أن التطبيق منشور أو معتمد من Google Play.
